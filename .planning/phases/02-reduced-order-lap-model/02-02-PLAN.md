**Scenario schema extension (packages/domain/src/scenario/schema.ts):**

Add a Zod schema for vehicle parameters at the scenario level:
- `vehicleParamsSchema`: `z.object({ mass: z.number().positive(), dragFactor: z.number().nonnegative(), downforceFactor: z.number().nonnegative(), peakPower: z.number().positive(), gripCoefficient: z.number().positive() }).strict()`.
- Add `vehicleParams: vehicleParamsSchema.optional()` to `scenarioDocumentSchema`. Making it optional preserves backward compatibility -- Phase 1 scenarios without vehicleParams remain valid. When absent, the model uses `DEFAULT_VEHICLE_PARAMS` at run time.
- Export `vehicleParamsSchema` and the inferred `VehicleParamsInput` type from the domain index.

**Default scenario update (packages/domain/src/scenario/defaultScenario.ts):**

Update `createDefaultScenario()` to include a `vehicleParams` field set to the default 2026 values (mass: 798, dragFactor: 1.05, downforceFactor: 3.8, peakPower: 735000, gripCoefficient: 1.7). Keep the existing circuit selection pointing to "monza" as the default circuitId.

**Run record schema extension (packages/domain/src/runs/schema.ts):**

The existing `summaryMetrics: z.record(z.string(), z.unknown())` is intentionally loose and already supports Phase 2's richer data. No schema change needed -- the lap model output (vehicleParams, circuitId, lapTime, sectorResults, speedProfile, assumptions) will be stored as fields within summaryMetrics. The run record's `modelVersion` field distinguishes Phase 1 vs Phase 2 runs.

However, check whether `createRunRecord` needs any update to handle the new output shape. The existing `output.summaryMetrics` field is already `Record<string, unknown>`, so it should accept Phase 2 data without changes. Verify this.

**Circuit API route (apps/local-api/src/routes/circuits.ts):**

Create a new route file:
- `GET /api/circuits` -- loads circuit catalog from `paths.presetsRoot + "/circuits"` using `loadCircuitCatalogFromDisk`, returns the array of `CircuitDocument` objects. This gives the browser a list of available circuits for the selector dropdown.
- Register in `apps/local-api/src/app.ts` alongside existing route registrations.

**Run service extension (apps/local-api/src/services/runService.ts):**

Add a new function `createLapModelRun(paths: LocalApiPaths, input: CreateLapModelRunInput): Promise<RunRecord>` alongside the existing `createPhase1Run`:

1. Load the saved scenario (same pattern as `createPhase1Run`).
2. Resolve preset documents (same pattern).
3. Load the circuit document: Use `loadCircuitCatalogFromDisk(join(paths.presetsRoot, "circuits"))` to get all circuits, then find the one matching `scenario.circuit.circuitId`. If not found, throw `RunDependencyError`.
4. Determine vehicle params: If `scenario.vehicleParams` exists, use those. Otherwise use `DEFAULT_VEHICLE_PARAMS` from sim-core.
5. Call `solveLap(circuitDocument, vehicleParams)` from sim-core.
6. Build the run record using `createRunRecord` with:
   - `modelVersion: "qss-lap-model/v1"`
   - `summaryMetrics`: `{ harnessId: "qss-lap-model", circuitId, vehicleParams, lapTime, sectorResults, speedProfile (truncated to avoid huge files -- store every Nth point, e.g. every 10th, in summaryMetrics but full profile in an artifact), assumptions }`.
   - `artifacts`: One artifact `{ artifactId: "${runId}-speed-profile", artifactType: "qss-speed-profile", label: "Full speed-vs-distance profile", data: { speedProfile: lapOutput.speedProfile, sectorResults: lapOutput.sectorResults } }`.
   - `assumptionNotes`: Map each assumption string to `{ note, provenance: { sourceType: "engineering-inference", source: "QSS lap model (Lenzo & Rossi 2020)", notes: "..." } }`.
7. Persist and return the run record.

**Important context budget note for the speed profile:** A Monza circuit at 5m spacing produces ~1159 SpeedProfilePoints. Each point is ~7 numeric fields. Storing the full profile in `summaryMetrics` is fine for JSON persistence (the file will be ~100-200KB). Store the full profile in the artifact's data field. In summaryMetrics, store a sampled subset (every 10th point) for quick display, plus the full sectorResults and scalar metrics (lapTime, circuitId, vehicleParams, assumptions).

**Run route update (apps/local-api/src/routes/runs.ts):**

Extend the `POST /runs` route to accept an optional `harnessId` field in the request body:
- If `harnessId === "qss-lap-model"` (or absent with a scenario that has vehicleParams), call `createLapModelRun`.
- If `harnessId === "phase1-placeholder"`, call the existing `createPhase1Run`.
- Default behavior: if the scenario has `vehicleParams` and a known `circuitId`, use the lap model. Otherwise fall back to the placeholder. This ensures backward compatibility.
