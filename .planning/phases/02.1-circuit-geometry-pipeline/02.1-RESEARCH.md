# Phase 2.1 Research: Circuit Geometry Pipeline

**Researched:** 2026-03-27
**Phase:** 02.1-circuit-geometry-pipeline
**Status:** Complete

---

## Summary

The circuit geometry pipeline should use TUMFTM racetrack-database as the primary data source for Monza and Silverstone, and bacinger/f1-circuits GeoJSON as the fallback for Monaco (which TUMFTM does not cover). Both sources provide real GPS-derived centerline coordinates that will replace the current hand-authored x/y data. The recommended implementation is a Python script using only numpy and scipy (already available on the system), not Node.js, because the spline math is simpler and more robust in scipy.

**The key finding:** TUMFTM Monza and Silverstone data is already at ~5m spacing with a closure gap of ~5m (matching our array convention), making it a near-direct import with only spline smoothing and distance indexing needed. Monaco requires the bacinger GeoJSON path with a coordinate projection step. In both cases, the existing curvature arrays in the preset files should be **kept** for lap model physics — TUMFTM-derived curvature has GPS noise that produces physically implausible corner radii (as low as 10m at Variante del Rettifilo, where the real apex radius is ~45m). The pipeline should replace x/y only.

## Standard Stack

### Data Sources

**TUMFTM racetrack-database** (https://github.com/TUMFTM/racetrack-database)
- License: LGPL-3.0
- Covers: 25 circuits including Monza and Silverstone; Monaco is absent
- Format: CSV with header `# x_m,y_m,w_tr_right_m,w_tr_left_m`
- Coordinate system: local meters (x_m, y_m), origin near the start/finish line, arbitrary orientation relative to north
- Point spacing: ~5m (confirmed: Monza mean 4.996m, stdev 0.044m; Silverstone mean 5.00m)
- Closure: N points representing a closed loop. The last point is one segment-length (~5m) before the first point. Closing the loop requires treating the array as periodic (append first point to form an N+1-element open polyline, or use periodic spline).
- Track width: separate right/left half-widths in meters (Monza: 3.64–6.29m right, 3.69–6.13m left)
- Source data: GPS centerlines extracted from OpenStreetMap, smoothed with a proprietary algorithm, track widths from satellite image processing
- Last updated: ~2020 (no changes since; 0 open issues in repo)

**Verified TUMFTM data (direct download and analysis):**

| Circuit    | Points | Arc Length | Closure Gap | Extent (E-W × N-S) |
|------------|--------|------------|-------------|---------------------|
| Monza      | 1,159  | 5,790.2 m  | 4.998 m     | 1,254 × 2,171 m     |
| Silverstone| 1,179  | 5,881.8 m  | 5.001 m     | — (not measured)    |
| Monaco     | absent | —          | —           | —                   |

The Monza extent (1254m × 2171m) matches known circuit dimensions (~1250m E-W × ~1800m N-S), confirming the geometry is correct.

**bacinger/f1-circuits** (https://github.com/bacinger/f1-circuits)
- License: MIT
- Covers: 40 circuits including Monaco (mc-1929.geojson)
- Format: GeoJSON LineString, WGS84 (lon, lat) coordinates
- Monaco: 160 points (including duplicate endpoint that closes the loop), average spacing 20.9m, range 4.7–145.9m (very irregular), arc length 3,324m (bacinger metadata says 3,337m)
- Closure: First and last coordinate are identical — the GeoJSON LineString is already closed
- Silverstone (gb-1948) and Monza (gb-1948 / it-1953): also present but it-1953 is **Imola** (Autodromo Enzo e Dino Ferrari), not Monza. TUMFTM Monza data is preferred.

**Monaco resolution limitation:** bacinger Monaco has only 159 unique points at ~21m average spacing (some gaps up to 145m). Cubic spline interpolation will smooth over sharp low-speed corners (Hairpin, Rascasse, Portier). This is sufficient for a visually recognizable track map but underestimates peak curvature. The spline-derived max curvature was 0.1548 1/m (R=6.5m), which is actually too high at isolated points, while the mean |k| is reasonable. Treat Monaco as "approximate shape, sufficient for visualization" until a higher-resolution source is added.

**FastF1 telemetry** (https://github.com/theOehrly/Fast-F1)
- Can extract ~300–450 position points per lap from telemetry, covering all circuits including Monaco
- Requires loading a full session (~200–500MB download), a cache directory, and is deferred to Phase 6
- FastF1 is not installed in any conda environment on this machine; installing it is out of scope for Phase 2.1
- The `session.get_circuit_info()` data is described as "manually created and not highly accurate" — it provides corner markers and rotation, not a circuit centerline

## Architecture Patterns

### Pattern 1: TUMFTM CSV → CircuitDocument (Monza, Silverstone)

The pipeline is straightforward because TUMFTM spacing already matches our 5m convention:

```python
# 1. Parse CSV
pts = np.array([[x, y] for x, y in rows])             # shape (N, 2), N~1159
widths_r = np.array([w_right for ... in rows])         # optional, for future use
widths_l = np.array([w_left for ... in rows])

# 2. Close loop by appending first point
pts_closed = np.vstack([pts, pts[0]])                  # shape (N+1, 2)

# 3. Fit periodic cubic B-spline (s=0: interpolating, s>0: approximating)
tck, u = splprep([pts_closed[:,0], pts_closed[:,1]],
                 s=0, per=True, k=3)

# 4. Evaluate at uniform arc-length parameter (endpoint=False for open arrays)
total_s = compute_arc_length(pts_closed)               # ~5790 for Monza
n_out = round(total_s / 5)                             # ~1158 points
t_uniform = np.linspace(0, 1, n_out, endpoint=False)
x_new, y_new = splev(t_uniform, tck)

# 5. Distance index
distances = np.linspace(0, total_s, n_out, endpoint=False)

# 6. Build CircuitDocument points
points = [{"distance": float(d), "curvature": existing[i].curvature,
           "x": float(x), "y": float(y)}
          for i, (d, x, y) in enumerate(zip(distances, x_new, y_new))]
```

The `per=True` parameter in `splprep` creates a periodic spline that guarantees smooth connection at the wrap-around point. The `endpoint=False` convention matches our schema: `points[-1].distance = totalLength - 5` and the curve closes by wrapping.

**Verified:** This pipeline runs end-to-end. Output for Monza: 1,158 points at 5.000m spacing, arc length 5,790.2m, closure gap 5.0m (correct for the open-array convention).

### Pattern 2: bacinger GeoJSON → CircuitDocument (Monaco)

GeoJSON coordinates are WGS84 (lon, lat). A local equirectangular projection is sufficient for Monaco's ~735m × ~975m footprint:

```python
# 1. Load GeoJSON
coords = data['features'][0]['geometry']['coordinates']  # [[lon, lat], ...]
# Note: bacinger Monaco has coords[0] == coords[-1] (closed)

# 2. Drop duplicate endpoint
pts_geo = coords[:-1]                                    # 159 unique points

# 3. Project to local meters (equirectangular, sufficient for <5km extent)
lat_ref = mean([c[1] for c in pts_geo])
lon_ref = mean([c[0] for c in pts_geo])
R = 6_371_000  # Earth radius in meters

def project(lon, lat):
    x = R * math.radians(lon - lon_ref) * math.cos(math.radians(lat_ref))
    y = R * math.radians(lat - lat_ref)
    return x, y

pts = np.array([project(lon, lat) for lon, lat in pts_geo])

# 4–6: Same as TUMFTM pipeline (close loop, fit spline, resample at 5m)
```

**Verified:** Monaco pipeline produces 665 points at 5.00m spacing, arc length 3,322m (vs. real 3,337m; 0.4% error from projection). The projection error is negligible for visualization.

### Pattern 3: Curvature Decision (Do Not Re-derive from Geometry)

Curvature derived from the TUMFTM GPS centerline has GPS noise that creates physically implausible corner radii. Testing showed:

| Method | Monza Variante del Rettifilo peak |
|--------|-----------------------------------|
| Hand-authored | R = 35m (apex) |
| TUMFTM raw finite-difference | R = 10m — physically impossible |
| TUMFTM + Savitzky-Golay (window=21) | R = 27m — still too tight |
| TUMFTM spline (s=0) | R = 9m — worst |

Real Variante del Rettifilo: apex radius ~45m, minimum ~30m. The OSM GPS data has insufficient accuracy (~3m GPS error) to reliably recover curvature via numerical differentiation. Smoothing helps but cannot eliminate the noise without also washing out corner detail.

**Decision: Keep the existing hand-authored curvature arrays. Replace only x, y.** This is the correct separation: TUMFTM gives us spatial shape (what it looks like), hand-authored curvature gives us physics (how fast corners are traversed). These are independent fields in CircuitDocument.

The exception: if a future source provides surveyed curvature data (e.g., from professional lap simulation tools or LIDAR surveys), that can replace the curvature arrays with full regression testing.

### Pattern 4: Curvature Re-indexing

The existing presets have a different point count from what TUMFTM will produce:

| Circuit | Existing points | TUMFTM points (5m) |
|---------|-----------------|--------------------|
| Monza | 1,157 | 1,158 |
| Silverstone | 1,168 | 1,178 |

The curvature arrays are at 5m spacing by design, so a simple re-index by distance is valid. The existing curvature is parametric in arc length, so:

```python
# Re-index existing curvature to new distance array
import numpy as np

old_distances = [p['distance'] for p in old_points]     # existing 5m grid
old_kappas = [p['curvature'] for p in old_points]
new_distances = np.linspace(0, total_s, n_out, endpoint=False)

# Linear interpolation (fine for smooth curvature profiles)
new_kappas = np.interp(new_distances, old_distances, old_kappas,
                       period=old_distances[-1] + 5)    # wrap at totalLength
```

This preserves the physics model while aligning the distance index to the new spatial geometry.

Alternatively: the pipeline can normalize old_distances to [0,1] and new_distances to [0,1] before interpolating, which handles different total lengths.

### Constrained Optimization Approach (Mathematical Framing)

The user asked about treating circuit layout as a constrained optimization problem. The mathematical structure is:

**Problem:** Given curvature κ(s) at discrete arc-length positions s₀…sₙ, find (x(s), y(s)) such that:
1. x(0) = x(L), y(0) = y(L) — closure constraint
2. dx/ds = cos θ(s), dy/ds = sin θ(s) — Frenet-Serret compatibility
3. dθ/ds = κ(s) — curvature definition

This is an **ODE initial value problem**, not an optimization problem per se. The solution by numerical integration:
- θ(s) = θ₀ + ∫₀ˢ κ(σ) dσ (heading from curvature)
- x(s) = x₀ + ∫₀ˢ cos θ(σ) dσ
- y(s) = y₀ + ∫₀ˢ sin θ(σ) dσ

The closure constraint becomes an optimization target: find θ₀ (initial heading) such that (x(L), y(L)) = (x(0), y(0)).

This is exactly how the existing `generate-circuits.ts` script works (Euler integration). The problem is that integration error accumulates along the lap: for our hand-authored curvature arrays, the total accumulated heading does not satisfy ∫₀ᴸ κ ds = 2π (one full rotation for a clockwise circuit), producing the 2km closure gap.

The constrained optimization framing becomes useful as a **post-correction** or **validation** step:
- Fix closure: shift total curvature by Δκ = (2π - ∫κ ds) / L (uniform offset), or optimize initial heading
- Scipy has `minimize` with constraints or `scipy.optimize.fsolve` for finding the θ₀ that closes the curve

**Conclusion:** This approach is a useful diagnostic and correction tool for the hand-authored curvature, but it is not needed for Phase 2.1 because TUMFTM provides real x/y directly. It is worth documenting as the fallback for circuits without external data.

## Common Pitfalls

### 1. Confusing the closure convention

TUMFTM provides N points representing N closed segments. The last point is NOT coincident with the first — they are ~5m apart, and the circuit closes by connecting last→first. This is the correct convention for our CircuitDocument schema (points are at distances 0, 5, 10, ... L-5). Do not append the first point to the output array; doing so would create a duplicate at distance L that violates the schema.

When fitting the spline, append the first point as the (N+1)th knot to make the geometry closed, then evaluate at `linspace(0, 1, N, endpoint=False)`.

### 2. The bacinger `it-1953.geojson` is Imola, not Monza

`it-1953.geojson` has properties `Name: "Autodromo Enzo e Dino Ferrari"` and `Location: "Imola"`. It is the Emilia-Romagna circuit, not Monza (Autodromo Nazionale di Monza). Use TUMFTM `Monza.csv` for Monza.

### 3. Curvature from GPS is noisy and should not replace hand-authored values

Testing showed that even with Savitzky-Golay smoothing (window=21, poly=3), TUMFTM-derived curvature at Monza's Variante del Rettifilo is R=27m, versus the real ~45m apex radius and the hand-authored ~35m. GPS accuracy of ~3m over 5m segment lengths means curvature errors of order (3m)/(5m)² = 0.12 1/m, which is comparable to the curvature magnitude at slow corners.

### 4. splprep `s=0` vs `s>0`

`s=0` creates an interpolating spline that passes through all input points. This preserves GPS noise. `s>0` creates an approximating spline that smooths noise but may lose geometric accuracy. For Phase 2.1 (visualization only), `s=0` is recommended — it preserves the GPS centerline shape exactly, and the small-scale noise does not affect visual recognition. If curvature is to be re-derived in a future phase, `s>0` with tuning becomes necessary.

### 5. Monaco resolution is lower than Monza/Silverstone

bacinger Monaco has 159 unique points at ~21m average spacing with gaps up to 145m. The spline will smooth over tight corners. The track outline will be recognizable (Hairpin, the swimming pool section, the harbor chicane) but corner apexes will appear rounder than reality. This is acceptable for Phase 2.1's visualization goal.

### 6. Silverstone arc length vs preset totalLength

TUMFTM Silverstone arc length is 5,881.8m. The current preset has totalLength: 5891 (from bacinger metadata). After the pipeline update, totalLength should reflect the TUMFTM arc length (5,881.8m, or round to 5882). The difference is 0.15% and does not affect lap time simulation at the current fidelity.

### 7. Sector and corner distance annotations must survive the update

The existing presets have 3 sectors and 11 corners (Monza) with `startDistance`, `endDistance`, `apexDistance` values. These are in meters along the current 5m-spaced distance index. After re-indexing to TUMFTM geometry, distances may shift slightly because TUMFTM totalLength differs from hand-authored totalLength. The script must either: (a) preserve sector/corner annotations by re-interpolating distances proportionally (safe), or (b) require manual review after running. Option (a) is automated and correct to within the 5m resolution.

### 8. Do not use `per=True` with bacinger GeoJSON directly

The bacinger GeoJSON has coords[0] == coords[-1]. Remove the duplicate endpoint before passing to splprep, or splprep will create a knot discontinuity.

## Open Questions

### Resolved

**Q: Does TUMFTM cover all three target circuits?**
A: No. TUMFTM covers Monza and Silverstone but not Monaco. Monaco must use bacinger/f1-circuits GeoJSON as the source. Confirmed by direct inspection of the repository file listing.

**Q: What is the TUMFTM CSV coordinate system?**
A: Local meters, arbitrary origin near the start/finish line, scale in meters. No geographic reference is embedded. No transformation is needed — the coordinates are already in the local frame our schema expects. The origin can remain wherever TUMFTM placed it (near x=0, y=0).

**Q: What is the TUMFTM closure gap?**
A: ~5m (one segment spacing). This is correct: the array represents a closed loop where the last point connects back to the first. Our schema's open-array convention (points at 0, 5, 10, ..., L-5m) matches this exactly.

**Q: Is the constrained optimization approach needed?**
A: Not for Phase 2.1. TUMFTM provides real x/y directly. The optimization framing is useful for: (1) understanding why the existing hand-authored data doesn't close, (2) as a potential closure-correction pass for the existing curvature arrays in circuits without external data, (3) as a future phase when generating circuits from scratch. Document it but do not implement it in Phase 2.1.

**Q: Should curvature be re-derived from imported geometry?**
A: No. GPS-derived curvature from TUMFTM data has significant noise (R as low as 10m at corners where the real minimum is ~30–45m). Savitzky-Golay smoothing improves this but cannot eliminate the noise without a tuning process. The hand-authored curvature is physically more plausible and should be kept for the lap model. The pipeline should update x and y only.

**Q: What projection is needed for Monaco GeoJSON?**
A: Equirectangular projection centered on the circuit centroid. This is a simple (lon-lon_ref) × R × cos(lat_ref), (lat-lat_ref) × R calculation. For a circuit of 735m × 975m extent, the distortion is well under 0.1% (equirectangular error is proportional to the square of the angular extent). pyproj is not installed and is not needed.

**Q: Python or Node.js for the pipeline?**
A: Python. Reasons: (1) scipy.interpolate.splprep is the standard tool for periodic B-spline fitting of curves; the Node.js ecosystem has no equivalent without a significant dependency; (2) numpy/scipy are already installed in the base Python environment; (3) the pipeline is a one-time build step, not part of the monorepo runtime — language consistency with the monorepo is not a constraint; (4) the existing `generate-circuits.ts` produces the JSON that this pipeline replaces, so the output format is identical regardless of the script language.

**Q: How does TUMFTM handle circuits not in OSM?**
A: It doesn't — circuits must have a quality OSM trace. Monaco appears to lack a usable OSM centerline in the TUMFTM smoothing pipeline (likely because Circuit de Monaco runs on public roads that are mapped differently from permanent race tracks, making automated centerline extraction unreliable). bacinger constructs its data differently and has Monaco.

### Genuine Gaps

**G1: Monaco curvature quality for future improvement**
The bacinger Monaco data at 159 points / 21m spacing will produce a visually recognizable track but underestimated corner curvatures at tight sections (Hairpin, Rascasse). A future improvement would extract Monaco from FastF1 telemetry (300–450 points, GPS-based, covers all corners). This is deferred to Phase 6 per the context document.

**G2: TUMFTM Monza corner radius accuracy**
The TUMFTM centerline produces peak corner radii around 10m (from finite-difference curvature) where reality is 30–100m. This is a GPS accuracy issue in the OSM source data, not a TUMFTM smoothing failure. The shape is geometrically correct (correct circuit outline) but the x/y data has meter-scale noise at corner apexes. This is acceptable for visualization but means curvature derived from this data is unreliable. The x/y will produce a recognizable Monza map; the lap model physics use the hand-authored curvature.

**G3: Sector and corner distance drift**
When the pipeline re-indexes curvature from the old distance array (totalLength=5785m) to the new TUMFTM arc length (5790.2m), sector and corner distances will drift proportionally (~0.09%). This is sub-5m and invisible in visualization, but it means the corner annotations no longer precisely align with the named corner apexes in the geometry. A Phase 3+ improvement would re-derive corner annotations from the geometry directly (find local curvature maxima, match to known corner names).

**G4: Future circuits without TUMFTM coverage**
Phase 2.1 only needs Monza, Monaco, Silverstone. For future circuits not in TUMFTM (e.g., Singapore, Jeddah, Miami — all added after TUMFTM's ~2020 update), the options are: bacinger GeoJSON (lower resolution), FastF1 telemetry (requires Phase 6), or OSM Overpass API extraction (requires custom filtering). The pipeline should be structured to accept any x/y centerline source, not hardcode TUMFTM paths.

## Pipeline Recommendation

A single Python script (`scripts/build-circuit-geometry.py`) with the following structure:

```
scripts/
  build-circuit-geometry.py    # standalone, no project imports
  circuit-sources.json         # declares data source for each circuit
```

The script:
1. Downloads TUMFTM CSV or bacinger GeoJSON (or reads from local cache in `presets/circuits/sources/`)
2. Projects to local meters (equirectangular for GeoJSON; no-op for TUMFTM)
3. Fits periodic cubic spline with `splprep(..., s=0, per=True, k=3)`
4. Evaluates at uniform 5m spacing with `endpoint=False`
5. Re-indexes existing hand-authored curvature to new distance array (linear interpolation)
6. Preserves existing sectors, corners, and provenance structure
7. Writes updated JSON to `presets/circuits/`
8. Optionally prints a terminal sanity check (closure gap, point count, arc length, bounding box)

The script should be runnable as:
```bash
python3 scripts/build-circuit-geometry.py --circuit monza
python3 scripts/build-circuit-geometry.py --circuit monaco
python3 scripts/build-circuit-geometry.py --all
```

Runtime is under 5 seconds per circuit (no session loading, no large downloads beyond the CSV/GeoJSON files which are under 100KB each).

The existing `scripts/generate-circuits.ts` is superseded by this script for the x/y coordinate generation path, but the TypeScript file documents the hand-authored curvature profiles and segment geometry and should be kept as reference.
