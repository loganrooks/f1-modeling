# Phase 2.1: Circuit Geometry Pipeline - Context

**Gathered:** 2026-03-27
**Status:** Ready for research

<domain>
## Phase Boundary

Replace the hand-authored, non-closing x/y circuit coordinates with real geometry data so track map visualizations resemble actual circuits. The curvature arrays driving the lap model physics are adequate (lap times within 6-10% of reality) — this phase fixes the spatial visualization data, not the model.

Deliverable: Monza, Monaco, and Silverstone circuit presets with accurate x/y coordinates that produce recognizable track outlines in the TrackMap component. A reproducible pipeline for generating or converting circuit geometry so future circuits don't require hand-authoring.

This phase does NOT change the lap model, the forward-backward solver, or the simulation output. It only fixes the geometry data consumed by visualization.

</domain>

<assumptions>
## Working Model & Assumptions

### Data source strategy
The most likely approach is importing centerline data from the TUMFTM racetrack database (19 F1 circuits, ~3m spacing, GPS-derived from OSM) and converting it to our CircuitDocument format. This is a working assumption — research should evaluate whether TUMFTM data quality is sufficient and whether constrained optimization of our existing curvature arrays is a better or complementary approach.

### Curvature derivation
If we import x/y centerline data from an external source, we can derive curvature from the geometry (finite differences on heading angle) rather than hand-authoring it. This would give us both accurate spatial coordinates AND curvature derived from the same source — potentially improving model accuracy too. Research should evaluate whether TUMFTM-derived curvature is better than our current hand-authored curvature.

### Constrained optimization as alternative
The user specifically suggested treating circuit layout as a constrained optimization problem: fit x/y coordinates to satisfy closure (start = end), known corner locations, and total track length. This could work with our existing curvature arrays or as a correction pass on imported data. Research should evaluate feasibility and whether it adds value over direct import.

### Pipeline scope
The conversion pipeline likely runs as a one-time build step (Python script or Node script) that reads external data and writes circuit JSON preset files. It does NOT need to run at application runtime.

</assumptions>

<decisions>
## Implementation Decisions

### Data provenance must be honest
Circuit geometry sourced from external databases must carry accurate provenance documenting the source, its accuracy limitations, and how it was processed. The existing `provenance` and `assumptionNotes` fields in CircuitDocument are the right place for this.

### Existing schema is preserved
The CircuitDocument schema (circuitPointSchema with distance, curvature, optional x/y) is the right structure. This phase fills in accurate x/y values and potentially improves curvature — it does not redesign the schema.

### Claude's Discretion
- Choice of conversion pipeline language (Python for TUMFTM/FastF1 compatibility vs Node for consistency with the monorepo)
- Whether to derive curvature from imported geometry or keep existing curvature arrays
- Exact interpolation/resampling approach to match our 5m spacing convention
- Whether to include track width data from TUMFTM (could be useful for future lateral dynamics in Phase 3)

</decisions>

<constraints>
## Derived Constraints

### From Phase 2 codebase

1. **CircuitDocument schema** (`packages/domain/src/circuits/schema.ts`): Points have distance, curvature, optional x/y, optional elevation. Sectors have index/name/start/end distances. Corners have index/name/apex/entry/exit distances. Schema version is `"circuit-document/v1"`.

2. **TrackMap component** (`packages/visuals/src/workspace/TrackMap.tsx`): Renders SVG from `points[].x` and `points[].y`. Uses HSL speed-hue gradient overlay. Falls back to TrackContextPlaceholder when spatial data is absent. Already handles coordinate scaling and aspect ratio.

3. **Circuit preset files** (`presets/circuits/*.json`): Three files exist (monza.json, monaco.json, silverstone.json) with ~1160 points each at 5m spacing. The x/y data is fabricated and must be replaced. The curvature data may also be improvable.

4. **Sector and corner annotations**: Current presets have named sectors (3 per circuit) and named corners. These must be preserved or re-derived from the new geometry data.

5. **CircuitCatalog loader** (`packages/domain/src/node/circuitCatalog.ts`): Loads and validates circuit JSON from disk. No changes needed — the schema is unchanged.

6. **Lap model sensitivity**: Changing curvature values will change lap times. If curvature is re-derived from imported geometry, the new lap times must still be plausible (within 5-15% of real-world). Regression tests exist for this.

### From deliberation (f1-data-landscape-and-circuit-geometry-sources.md)

7. **TUMFTM racetrack database**: 19 F1 circuits, CSV format `[x_m, y_m, w_tr_right_m, w_tr_left_m]`, ~3m spacing, LGPL-3.0. Covers Monza, Monaco, Silverstone. GPS centerlines from OSM, smoothed. Last updated ~2020.

8. **bacinger/f1-circuits**: 37+ circuits, GeoJSON WGS84 lat/lon, MIT, ~33m spacing. Actively maintained through 2026. Lower resolution but wider coverage.

9. **FastF1 telemetry**: Can extract car position data from fastest laps, ~300-450 points/lap, ±10m jitter. Requires Python + session loading. No subscription needed.

10. **F1TV subscription not required**: Live timing API is unauthenticated. FastF1 accesses all telemetry data without subscription.

### From user feedback

11. **Constrained optimization**: The user specifically asked for circuit layout to be treated as a constrained optimization problem with closure constraints (start = end). This approach should be evaluated by research even if external data import is the primary path.

</constraints>

<questions>
## Open Questions

### 1. Should we import TUMFTM centerline data directly, or use constrained optimization on our existing curvature arrays, or both?
- **Type:** material
- **Why it matters:** Direct import gives real GPS geometry but may not match our curvature exactly. Constrained optimization preserves our curvature but reconstructs spatial coordinates. A hybrid (import x/y from TUMFTM, then re-derive curvature from that geometry) might give the best of both.
- **Downstream decision:** Whether the pipeline reads external CSV/GeoJSON or processes our existing JSON. Whether curvature values change (affecting lap times).
- **Reversibility:** High — the pipeline is a preprocessing step that can be re-run.
- **Research should:** Evaluate all three approaches. Compare TUMFTM geometry quality against known track shapes. Test whether TUMFTM-derived curvature produces plausible lap times. Evaluate whether constrained optimization adds value over direct import.

### 2. What coordinate system conversion is needed for TUMFTM data?
- **Type:** formal
- **Why it matters:** TUMFTM uses local x_m/y_m coordinates (meters, origin varies). Our circuit schema uses local-frame meters. The conversion may be trivial (just recenter) or may need rotation/scaling to match our convention.
- **Downstream decision:** Pipeline implementation details.
- **Reversibility:** High.
- **Research should:** Download and inspect actual TUMFTM data for Monza, Monaco, Silverstone. Determine coordinate system, origin, and whether any transformation is needed.

### 3. How should we handle circuits not covered by TUMFTM?
- **Type:** efficient
- **Why it matters:** TUMFTM covers 19 circuits (last updated ~2020). Phase 2 only needs Monza/Monaco/Silverstone (all covered), but future circuit additions will need a fallback strategy.
- **Downstream decision:** Whether the pipeline supports multiple data sources or is TUMFTM-specific.
- **Reversibility:** High — additional sources can be added later.
- **Research should:** Evaluate bacinger/f1-circuits GeoJSON as a fallback. Determine whether the constrained optimization approach could serve as a universal fallback for circuits without external data.

### 4. Should curvature be re-derived from imported geometry?
- **Type:** material
- **Why it matters:** Current curvature values produce plausible lap times (6-10% of reality). Re-deriving curvature from GPS geometry might improve or degrade accuracy depending on the quality of finite-difference curvature estimation on ~3m-spaced GPS data.
- **Downstream decision:** Whether lap times change after this phase. Whether existing test assertions need updating.
- **Reversibility:** Medium — changing curvature affects model output and may require re-tuning expectations.
- **Research should:** Compute curvature from TUMFTM Monza data and compare resulting lap time against both real-world and our current model output. Evaluate noise sensitivity of curvature estimation from GPS centerlines.

</questions>

<guardrails>
## Epistemic Guardrails

1. **Track shapes must be visually recognizable.** After this phase, plotting the x/y coordinates for Monza should produce a shape that a person familiar with the circuit would recognize. Compare against official F1 circuit maps.

2. **Tracks must close.** The last point's x/y must be within 5m of the first point's x/y. This was the primary failure of the Phase 2 hand-authored data.

3. **Provenance must be documented.** Each circuit preset must carry accurate provenance identifying the data source, its limitations, and any processing applied.

4. **Lap times must remain plausible.** If curvature values change, the resulting lap times must still be within 5-15% of real-world for the default vehicle parameters. Regression tests enforce this.

5. **Don't over-engineer the pipeline.** This is a preprocessing step for 3 circuits now, possibly more later. A script that works is better than a framework that's never needed.

</guardrails>

<specifics>
## Specific Ideas

- The user's constrained optimization framing: treat circuit layout as optimization with closure constraint (start = end), known corner positions, and total length. Even if we use TUMFTM data directly, this mathematical framing might be useful for validation or for circuits without external data.
- TUMFTM data includes track width (w_tr_right_m, w_tr_left_m) which could be useful for Phase 3's lateral dynamics. Consider preserving it even if Phase 2.1 doesn't use it.
- The pipeline could optionally output a visual validation plot (SVG or terminal ASCII) showing the track outline for quick sanity checking.

</specifics>
