# Phase 3.2: Backend Execution, Job Artifacts, and Regulation Execution Flow - Research

**Researched:** 2026-04-16
**Domain:** compiled execution requests, async job protocol, durable artifact storage, local worker backend, regulation execution snapshots
**Confidence:** MEDIUM-HIGH

## Summary

Phase 3.2 is a boundary-and-migration phase, not a new modeling-capability phase. The core work is to move existing placeholder, lap, stint, and race execution behind a durable `RunCommand -> CompiledSimulationRequest -> SimulationBackend` contract, persist artifacts independently from run records, and compile regulation data before execution instead of reading loose preset maps and hardcoded 2026 constants inside the runtime path.

The current codebase already contains the main execution kernels and reproducibility discipline needed for this move:

- `apps/local-api/src/services/runService.ts` already resolves scenarios, presets, circuits, tire compounds, weather, and artifacts, but all of that work is fused into one synchronous route-service seam.
- `packages/sim-core/src/*` already contains usable placeholder, lap, stint, and race kernels, so the first backend implementation can wrap those kernels rather than rewrite them.
- `packages/domain/src/runs/createRunRecord.ts` and `packages/domain/src/runs/schema.ts` already preserve snapshots and lineage, which makes a compatibility-first run-record migration realistic.
- `apps/web/src/features/workspace/api.ts` and `apps/web/src/app/useWorkspace.ts` still assume synchronous `POST /api/runs` plus inline artifact data, so Phase 3.2 needs a compatibility layer rather than a hard cut.

The main planning conclusion is that the migration should be staged in this order even though the roadmap numbering remains `01 -> 05`:

1. Define the durable execution contracts and compiler seam.
2. Land durable artifact storage and run-record compatibility before public job routes.
3. Put current execution behind the new backend boundary and split `runService.ts`.
4. Expose the public REST + SSE job surface on top of the real backend/store.
5. Remove raw-preset and 2026-specific regulation assumptions from the runtime path.

That sequencing is more honest than implementing public job routes first, because `artifact-ready` events and fetch semantics need real artifact IDs, persisted envelopes, and a backend that can produce distinct `jobId` and `runId` values.

## Primary Recommendations

### 1. Use one discriminated compiled-request family, not separate ad hoc backend entrypoints

The minimum useful Phase 3.2 request shape is one `CompiledSimulationRequest` family with a common base plus per-workload payload variants for:

- `phase1-placeholder`
- `qss-lap-model`
- `stint-model`
- `race-simulation`

The common base should carry:

- `schemaVersion`
- `requestId`
- `jobId`
- `runId`
- `runFamilyId`
- optional lineage (`parentRunId`, `branchPoint`)
- execution posture (`harnessId`, `checkpointPolicy`, `fidelityTier`, `backendHint`)
- scenario and preset snapshot hashes
- `ExecutionRegulationSnapshot`
- `inputDigest`

Why this is the right cut:

- It preserves a single transport-neutral backend contract for all current workloads.
- It keeps `jobId`, `runId`, `runFamilyId`, and later artifact IDs distinct from day one.
- It lets the local compiler resolve filesystem-only concerns without leaking those concerns into the backend interface.
- It preserves the current placeholder path as a compatibility workload instead of leaving it as a silent bypass.

### 2. Start with one job producing one run, but reserve `runFamilyId`

The first job topology should be:

- one submitted job
- one produced run
- optional `runFamilyId` spanning parent/branch descendants

Do **not** introduce parent/child jobs or comparison-batch orchestration in Phase 3.2.

Why:

- D1 left batch shape open.
- Current browser and API consumers do not need parent/child orchestration yet.
- `runFamilyId` is enough to keep branch lineage honest without committing to a scheduler model that later phases may not want.
- Phase 4 and 4.1 need branch grouping and durable fetch more urgently than they need a batch tree.

### 3. Migrate storage to artifact envelopes plus manifest-backed run records, with compatibility read models

The first credible migration is:

- **stored canonical form:** `run-record/v2` style manifest entries plus separate `ArtifactEnvelope` files
- **compatibility read model:** keep `GET /api/runs` and the legacy `POST /api/runs` wrapper able to return a materialized `RunRecord` shape with inline artifact payloads for the current web UI
- **read compatibility:** preserve readability for existing `run-record/v1` files rather than forcing destructive in-place migration

This is preferable to both extremes:

- **Manifest-only immediately:** would break the current web client, which still reads `run.artifacts[].data`.
- **Keep inline JSON as the canonical form:** would make durable fetch, artifact revisions, replay-safe events, and D2/D3 artifact identity weaker than the accepted D1 contract.

Planning consequence:

- `packages/domain` should distinguish stored run-record schemas from compatibility read-model schemas.
- `apps/local-api` should own materialization from stored runs plus artifact envelopes into the current web-facing read model until D2/D3 consume fetchable artifacts directly.

### 4. Use a long-lived local TypeScript worker process as the first backend implementation

The first backend should be a long-lived local TypeScript worker process managed by `apps/local-api`, not direct synchronous `sim-core` calls from route handlers.

Recommended shape:

- `apps/local-api/src/workers/localSimulationWorker.ts` executes compiled requests against existing `sim-core` kernels.
- `apps/local-api/src/services/localSimulationBackend.ts` implements `SimulationBackend`.
- The worker and backend communicate via explicit message payloads that mirror the domain job/event/artifact contract.

Why this is still the lowest-risk choice:

- It honors the D1 contract more faithfully than a cosmetic async wrapper around synchronous in-process calls.
- It keeps future sidecar or remote migration credible.
- It still reuses the current TypeScript kernels directly.
- It gives Phase 4 a real compute substrate without forcing a premature language rewrite.

### 5. Compile the execution-facing regulation slice now, not the full semantic registry

The minimum `ExecutionRegulationSnapshot` field set that clears the corridor is:

- source identity and hash
- family identity and optional family variant identity
- override lineage
- canonical semantic reference
- stable semantic identifiers for comparison-relevant concepts
- compiler version and execution snapshot hash
- capability modules for:
  - `aero`
  - `electrical`
  - `refueling`
  - `tireUsage` or equivalent execution-facing session/tire constraints

The snapshot should stay execution-facing. It should **not** attempt to close:

- the full D5 comparability/applicability registry
- historical family expansion
- lesson-facing semantic resolution
- `AnchorRegistry` or D2/D3 addressability design

Planning consequence:

- raw preset storage remains intact for authored reproducibility
- the compiler becomes the only place that turns raw regulation documents into runtime inputs
- `packages/sim-core/src/stintModel/electricalModel.ts` and `packages/sim-core/src/raceModel/raceRunner.ts` must stop depending on 2026-only constants and implicit no-refueling assumptions

### 6. Expose the D1 edge as additive REST + SSE while preserving the current run routes as compatibility wrappers

The thinnest honest edge is still:

- `POST /api/jobs`
- `GET /api/jobs/:jobId`
- `POST /api/jobs/:jobId/cancel`
- `GET /api/jobs/:jobId/events`
- `GET /api/jobs/:jobId/artifacts`
- `GET /api/artifacts/:artifactId`

Keep these compatibility rules:

- `GET /api/runs` stays as the current read-model listing endpoint.
- `POST /api/runs` becomes a compatibility wrapper that compiles a command, submits a job, waits for completion, materializes the run read model, and returns the same shape current web consumers expect.
- `apps/web` can gain job-aware API helpers in Phase 3.2, but the current shell does not need to fully switch over before Phase 3.3.

This preserves the existing workspace without canonizing its synchronous assumptions.

## Recommended Implementation Substrate

No new third-party dependencies are required for the planned Phase 3.2 work.

Use built-in platform primitives where possible:

- `node:crypto` for stable SHA-256 content hashes
- `node:child_process` or equivalent process-based worker bootstrap for the first backend
- Fastify route handlers plus SSE response streaming for `/api/jobs/:jobId/events`
- existing JSON file persistence under `workspace-data/`

That keeps the first boundary local-first and auditable.

## Compatibility And Migration Obligations

### Existing saved runs

Existing `workspace-data/runs/*.json` files are part of the current product contract. Phase 3.2 should therefore:

- continue to read `run-record/v1`
- write a new stored form for newly created runs
- avoid silent destructive conversion of historical files
- test both old and new stored run shapes through the same listing/materialization path

### Existing web consumers

Current web panels read inline artifact payloads directly. Phase 3.2 should therefore:

- preserve the current `RunRecord`-shaped response for `GET /api/runs`
- materialize artifact payloads for the known current artifact families:
  - `phase1-placeholder-trace`
  - `qss-speed-profile`
  - `stint-trace`
  - `tire-degradation-trace`
  - `electrical-state-trace`
  - `weather-evolution-trace`
  - `race-timeline`
- treat that materialization as a compatibility layer, not the new canonical artifact contract

### Existing tests

`apps/local-api/src/__tests__/raceRuns.test.ts` and related lap/stint tests should stay part of the migration safety net. New job/artifact tests should be added, not used as an excuse to weaken existing route coverage.

## Planning Consequences

### Recommended wave order

The roadmap numbering stays `03.2-01` through `03.2-05`, but the most honest execution waves are:

- Wave 1: `03.2-01`
- Wave 2: `03.2-03`
- Wave 3: `03.2-04`
- Wave 4: `03.2-02` and `03.2-05`

Why this is justified:

- public job routes without durable artifact IDs and a real backend would create a fake async surface
- artifact storage can be landed against the current synchronous run paths first
- the backend split should happen before external routes depend on it
- regulation cleanup can proceed in parallel with public edge-route work once the split compiler/backend seams exist

### Active tech debt handling

- `VA-TD-01` is paid during the backend split, not during contract definition.
- `VA-TD-02` is paid during regulation compilation and runtime cleanup, not by merely adding types.
- `VA-TD-03` is fired when the new backend contract becomes authoritative and is retired once public job semantics are live.

### Explicit deferrals to later phases

Keep these out of Phase 3.2:

- recipe-driven shell, shared interaction state, renderer-neutral contracts, `AccessibleChartContract`, `AnchorRegistry`, and benchmark harness work from Phase 3.3
- lesson schema, preview tooling, validation stack, surfaced applicability UI, and broader semantic registry work from Phase 3.4
- observer replay UI and checkpoint browsing from Phase 4.1
- remote/cloud backends and compute-language migration decisions

## Genuine Gaps

| Question | Why it remains open | Criticality | Recommendation | Planning consequence |
| --- | --- | --- | --- | --- |
| What exact worker bootstrap path should be used in dev vs built mode? | D1 fixes the boundary shape but not whether the first worker is launched through `tsx`, compiled JS, or a dedicated bootstrap wrapper. | Low | Accept-risk | Hide worker startup behind one local backend service so the bootstrap detail can change without affecting the public contract. |
| How much artifact data should the compatibility read model inline once artifacts are stored independently? | Current web panels need some inline payloads, but Phase 3.2 should avoid rebuilding a second canonical artifact system in the read model. | Medium | Accept-risk | Materialize only the artifact families current web panels actually consume; keep all other consumers on manifest-plus-fetch semantics. |

No spike-worthy or planning-blocking gaps remain. The unresolved items are implementation-calibration details, not reasons to delay the phase package.

## Still Open

- The exact replay-window implementation can vary, but only inside the accepted D1 short-window envelope: roughly 5-15 minutes of replayable history locally, or a tested deterministic equivalent that still satisfies reconnect expectations.
- The exact shape of `semanticApplicability` population stays deferred to Phase 3.4; Phase 3.2 only needs the reserved slot.
- The broader D5 relation vocabulary remains deferred, but stable semantic identifiers, override lineage, and a canonical semantic reference are not deferred; they are part of the 3.2 handshake.
- The exact child-job or batch scheduler model remains deferred until a later phase actually needs multi-run orchestration.
