## Vision Impact

This plan defines the **durable execution-domain authority line** that every later phase consumes (3.3 visualization, 3.4 lessons, 4.1 observer/replay, 6 telemetry import, 7 calibration, 8 regulation exploration). Three long-arc-protecting moves are load-bearing here:

1. **Transport-neutral execution boundary** (LONG-ARC § Protected Seams 1) — `SimulationBackend` as a typed contract that local-worker, sidecar, and remote backends can all satisfy. Without this the compute-anywhere doctrine remains aspiration.
2. **Typed artifact identity with provenance** (LONG-ARC § Protected Seams 3) — `ArtifactEnvelope` with lineage, provenance, fidelity, validation, and regulation references. These fields are required, not optional, because every downstream consumer relies on their honesty.
3. **Puzzle / skill-practice mode seam preservation** (LONG-ARC § Protected Seams 4 added 2026-05-15) — the envelope must reserve schema slots for selective-masking metadata, puzzle/scoring/judgment/reconstruction artifact subtypes, and difficulty metadata. Slot reservation only; semantics come with the future puzzle-mode initiative. See CONTEXT.md `<specifics>` § Puzzle-mode seam preservation and `.planning/initiatives/seeds/puzzle-mode-pedagogy.md`.

The structured `disposition: preserved_seam` annotations in this plan's frontmatter operationalize each of these claims at task granularity.

## Honesty Surface

This plan has no UI work, but the schemas it defines determine whether downstream panels can **visibly** label fidelity and validation per CLAUDE.md § Visible fidelity labeling. Required:

- `fidelityTier` and `validationState` are non-optional fields on `ArtifactEnvelope` — Phase 3.3 must always have something to render.
- `ExecutionRegulationSnapshot` carries the canonical semantic reference and override lineage so the runtime never has to guess "which regulation was actually applied" — the answer is in the envelope.
- No silent defaults. Missing capabilities raise an explicit error or an explicit not-applicable marker.

## Performance Budget

Schema-definition work; no runtime perf budget on this plan itself. Indirect obligation:

- The compiler seam (`compileRunCommand`) must be async-friendly so plan 03.2-02 can build the submit/get/cancel surface on top without blocking I/O regressions.
- No benchmark harness exists yet (Phase 3.3 § Plan 05 builds it). For now, manual smoke checks the dev-server submit path stays comparable to the pre-split baseline.
