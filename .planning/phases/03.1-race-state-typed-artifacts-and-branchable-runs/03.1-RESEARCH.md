## Summary

Phase 3.1 bridges single-stint simulation (Phase 3) and full race-strategy analysis (Phase 4). The core engineering challenge is orchestrating the existing `runStint()` function across multiple stints with pit events, race interruptions, and state continuity between stints, while producing typed timeline artifacts that Phase 4's comparison and explanation views can consume. Simultaneously, run records must carry lineage metadata for fork-from-state workflows, and tire-set inventory must track compound allocation across a weekend.

The codebase is well-positioned for this extension. The existing `StintRunner` returns `StintResult` with `finalState: StintState` containing tire, electrical, environment, and fuel state -- a natural handoff point between stints. The discriminated union pattern on `harnessId` in `contracts.ts` cleanly supports adding a `"race-simulation"` variant. All domain schemas use Zod `.strict()` mode, which means schema extensions require explicit new fields on the schema definition (not runtime ad-hoc additions), but the `scenarioDocumentSchema` already demonstrates the optional-extension pattern (`stintConfig: stintConfigSchema.optional()`). The `runRecordSchema` similarly uses `.strict()`, requiring explicit schema modification to add lineage fields -- this is a planned, small change, not a workaround.

Research into F1 pit-lane loss modeling, safety car effects, and tire allocation rules has resolved all six open questions from the CONTEXT.md to sufficient depth for planning. The pit-lane loss model follows the well-established `L_pit = (t_entry + t_exit - t_bypass) + t_stop` decomposition with circuit-specific parameters. Race interruptions for a single-car model reduce to lap-time deltas and pit-cost discounts (the "flag discount factor" phi). Tire allocation follows FIA rules: 13 sets per standard weekend (2H/3M/8S) with session return requirements.

**Primary recommendation:** Build the race-state engine as a thin orchestration layer that calls `runStint()` per stint, applies pit-event state mutations between stints, injects interruption effects as lap-time modifiers, and produces a typed discriminated-union event timeline. Start with stint-boundary branching only; design the state snapshot to be extensible to mid-stint forks later.

### Pattern 1: Race-State Engine as Stint Sequencer
**What:** The race engine iterates over an ordered stint array. For each stint, it resolves a StintConfig from the race plan, calls `runStint()`, collects the StintResult, applies pit-event state mutations to `finalState`, and feeds the modified state into the next stint's initialization. The engine tracks cumulative race time and builds a typed timeline of events.
**When to use:** All race simulation runs.
**Example:**
```typescript
// Pseudocode for race engine core loop
export function runRace(plan: RacePlan, config: RaceConfig): RaceResult {
  let currentState: StintState = initializeRaceState(plan, config);
  const timeline: RaceTimelineEvent[] = [];
  const stintResults: StintResult[] = [];
  let cumulativeTime = 0;

  for (let i = 0; i < plan.stints.length; i++) {
    const stintSpec = plan.stints[i]!;

    // Resolve StintConfig from race plan + current state
    const stintConfig = resolveStintConfig(stintSpec, config, currentState);

    // Run the stint (reuses existing runStint)
    const result = runStint(stintConfig);
    stintResults.push(result);

    // Record stint-start and stint-end events
    timeline.push({
      type: "stint-start",
      stintIndex: i,
      raceLap: currentState.lapNumber,
      compound: stintSpec.compound,
    });

    // Process any interruptions that fall within this stint's laps
    for (const interruption of plan.interruptions ?? []) {
      if (isWithinStint(interruption, currentState.lapNumber, stintConfig.totalLaps)) {
        timeline.push(createInterruptionEvent(interruption, cumulativeTime));
      }
    }

    cumulativeTime += result.totalTime;

    timeline.push({
      type: "stint-end",
      stintIndex: i,
      raceLap: currentState.lapNumber + stintConfig.totalLaps,
      stintTime: result.totalTime,
      cumulativeRaceTime: cumulativeTime,
    });

    // Apply pit-event mutations (unless last stint)
    if (i < plan.stints.length - 1) {
      const pitLoss = computePitLoss(config.pitParams);
      cumulativeTime += pitLoss.totalLoss;
      currentState = applyPitEvent(result.finalState, plan.stints[i + 1]!, pitLoss);

      timeline.push({
        type: "pit-event",
        afterStintIndex: i,
        raceLap: currentState.lapNumber,
        pitLoss,
        newCompound: plan.stints[i + 1]!.compound,
      });
    }
  }

  return { stintResults, timeline, totalRaceTime: cumulativeTime, ... };
}
```

### Pattern 2: Pit-Event State Mutation
**What:** Between stints, the race engine modifies the StintState to reflect a pit stop: new tires (fresh TireState for the next compound), electrical state carries through (SoC persists), environment state carries through, fuel state persists (no refueling in 2026). Tire-set inventory is decremented.
**When to use:** At every stint boundary except after the final stint.
**Example:**
```typescript
function applyPitEvent(
  finalState: StintState,
  nextStintSpec: StintSpec,
  pitLoss: PitLossResult,
): StintState {
  return {
    lapNumber: finalState.lapNumber,
    tireState: initializeTireState(
      nextStintSpec.tireCompound,
      finalState.environmentState.trackTemperatureC,
    ),
    electricalState: finalState.electricalState, // SoC carries through
    environmentState: finalState.environmentState, // Weather carries through
    fuelMass: finalState.fuelMass, // No refueling in 2026
  };
}
```

### Pattern 3: Discriminated Union Timeline Events
**What:** The race timeline is an ordered array of discriminated events using a `type` field. This enables downstream consumers to pattern-match on event types for rendering and analysis.
**When to use:** All race timeline artifacts.
**Example:**
```typescript
type RaceTimelineEvent =
  | { type: "stint-start"; stintIndex: number; raceLap: number; compound: CompoundId; policy: string }
  | { type: "stint-end"; stintIndex: number; raceLap: number; stintTime: number; cumulativeRaceTime: number }
  | { type: "pit-event"; afterStintIndex: number; raceLap: number; pitLoss: PitLossResult; newCompound: CompoundId }
  | { type: "interruption-start"; interruptionType: "vsc" | "sc" | "red-flag"; raceLap: number }
  | { type: "interruption-end"; interruptionType: "vsc" | "sc" | "red-flag"; raceLap: number };
```

### Anti-Patterns to Avoid
- **Baking lap-level discretization into public APIs:** Phase 5 may need a time-step interface. Keep the race engine's sequencing logic (stint-to-stint orchestration) separable from the stint runner's internal lap loop.
- **Stripping state snapshots from timeline events:** Phase 4.1's observer layer needs per-lap state to reconstruct measurement channels. Preserve full `LapTrace` detail in artifacts.
- **Making racePlan required on ScenarioDocument:** This would break all existing scenarios. Follow the `stintConfig` pattern: optional field, exclusive with `stintConfig`.
- **Using untyped `z.record(string, unknown)` for timeline artifacts:** The whole point of RACE-03 is typed artifacts. Use discriminated unions with Zod schemas.
- **Implicit experiment grouping from lineage tree traversal:** Siblings in a lineage tree are not necessarily exploring the same question. Use explicit experiment tags/IDs.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Pit-lane loss physics | Full pit-lane traversal simulation | Reduced-order time-loss formula `L_pit = (t_entry + t_exit - t_bypass) + t_stop` | Deceptively complex kinematics; reduced-order captures the strategy-relevant delta |
| Race interruption lap-time model | Full field-bunching simulation | Flag discount factor `phi` on lap times and pit costs | Single-car model cannot simulate field dynamics; phi captures the strategy-relevant effect |
| Tire allocation rule engine | Custom regulation parser | Configurable allocation table in regulation preset | Rules change by era; configuration beats code |
| UUID generation | Custom ID scheme | `crypto.randomUUID()` (Node.js built-in) | Standard, collision-resistant, no dependencies |
| Deep state cloning for branching | Manual field-by-field copy | `structuredClone()` (already used in `createRunRecord`) | Handles nested objects, avoids bugs |

**Key insight:** The pit-lane loss and interruption models are strategy-level abstractions, not physics simulations. Their value is in making pit timing and interruption response decisions meaningful, not in accurately simulating the pit lane traversal or safety car bunching. Reduced-order models with honest provenance labels serve the educational purpose better than false-precision simulations.

## Common Pitfalls

### Pitfall 1: Schema Migration Breaking Existing Runs
**What goes wrong:** Adding required fields to `runRecordSchema` or `scenarioDocumentSchema` causes existing saved JSON files to fail validation.
**Why it happens:** All schemas use `.strict()` and existing files lack new fields.
**How to avoid:** All new fields MUST be `.optional()`. Never add required fields to existing schemas. If a field is semantically required for race runs, validate it at the race engine level (runtime check), not at the schema level (parse-time check).
**Warning signs:** `z.ZodError` when loading existing scenarios or runs after schema changes.

### Pitfall 2: State Continuity Gaps at Stint Boundaries
**What goes wrong:** Race engine feeds `finalState` from stint N directly into stint N+1, but `initializeStintState()` in `stintRunner.ts` always creates fresh state from config, ignoring any provided initial state.
**Why it happens:** `runStint()` currently has no mechanism to accept a pre-existing state. It always calls `initializeStintState(config)`.
**How to avoid:** Either (a) add an optional `initialState` parameter to `runStint()`, or (b) create a new `runStintFromState(config, initialState)` function that skips initialization. Option (b) is safer -- it avoids changing the existing function signature.
**Warning signs:** Tire state resets to fresh at each stint instead of carrying over from pit stop.

### Pitfall 3: Cumulative Time Accounting Errors
**What goes wrong:** Race total time does not include pit-event time losses, or double-counts them.
**Why it happens:** Pit loss is a separate time cost not captured by any stint's `totalTime`. Easy to forget adding it to the cumulative total.
**How to avoid:** Centralize time accounting in the race engine loop. Each stint contributes `stintResult.totalTime`, each pit event contributes `pitLoss.totalLoss`, each interruption contributes its time delta. Sum all three categories.
**Warning signs:** Race total time equals sum of stint times (missing pit losses).

### Pitfall 4: Interruption Effects Applied Outside Their Lap Range
**What goes wrong:** A VSC specified for laps 15-18 affects lap times outside that range, or doesn't affect them at all because the stint boundaries don't align with the interruption laps.
**Why it happens:** Interruptions are specified in race-level lap numbers, but stints count laps from 0. The mapping between race-level and stint-level lap numbers requires careful accounting.
**How to avoid:** Maintain a `raceStartLap` counter that tracks the cumulative race lap at each stint start. Map interruption laps to stint-local laps: `stintLocalLap = interruptionLap - raceStartLap`.
**Warning signs:** Interruption effects appear at wrong points in the timeline or are silently ignored.

### Pitfall 5: Tire Inventory Not Validated Before Race Execution
**What goes wrong:** A race plan specifies 4 stints on soft tires, consuming 4 sets, but only 3 are available after qualifying. The engine happily simulates an impossible race.
**Why it happens:** Schema validation ensures types are correct but cannot enforce cross-field business rules (available sets vs. used sets).
**How to avoid:** Add a pre-execution validation step that checks the race plan's total compound usage against the tire inventory. Fail with a descriptive error if allocation is exceeded.
**Warning signs:** Race results that use more tire sets than the regulations allow.

### Pitfall 6: Branch State Snapshot Not Deep-Cloned
**What goes wrong:** Branching from a race state at stint boundary N creates a new run, but the branched run's initial state shares object references with the parent run's state, causing mutation side effects.
**Why it happens:** JavaScript object assignment is shallow.
**How to avoid:** Use `structuredClone()` when capturing state snapshots for branching. The codebase already uses this pattern in `createRunRecord.ts`.
**Warning signs:** Modifying the branched run's state retroactively changes the parent run's stored artifacts.

## Code Examples

### Pit-Lane Loss Model
```typescript
// Source: Race strategy modelling literature (Heilmeier et al., formula1.wiki)
// L_pit = (t_entry + t_exit - t_bypass) + t_stop
// Under safety conditions: L_pit_flag = phi * L_pit

export interface PitLaneParams {
  /** Time to decelerate from racing speed and traverse pit entry (seconds). */
  pitEntryTime: number;
  /** Time to accelerate from pit box and traverse pit exit (seconds). */
  pitExitTime: number;
  /** Time the car would take to cover the pit lane distance at racing speed (seconds). */
  pitBypassTime: number;
  /** Stationary service time (tire change, adjustments) in seconds. */
  serviceTime: number;
}

export interface PitLossResult {
  /** Total time lost relative to staying on track (seconds). */
  totalLoss: number;
  /** Breakdown: entry/exit overhead minus bypass savings. */
  traversalDelta: number;
  /** Breakdown: stationary service time. */
  serviceTime: number;
}

export function computePitLoss(params: PitLaneParams): PitLossResult {
  const traversalDelta = (params.pitEntryTime + params.pitExitTime) - params.pitBypassTime;
  const totalLoss = traversalDelta + params.serviceTime;
  return { totalLoss, traversalDelta, serviceTime: params.serviceTime };
}

// Typical circuit values (engineering-inference):
// Monza:       { pitEntryTime: 12, pitExitTime: 10, pitBypassTime: 5, serviceTime: 2.5 } => ~19.5s
// Monaco:      { pitEntryTime: 11, pitExitTime: 10, pitBypassTime: 3, serviceTime: 2.5 } => ~20.5s
// Silverstone: { pitEntryTime: 14, pitExitTime: 12, pitBypassTime: 4, serviceTime: 2.5 } => ~24.5s
```

### Race Interruption Flag Discount
```typescript
// Source: Race strategy modelling literature (formula1.wiki)
// Under VSC/SC, pit cost is reduced because the field is slower.

export type InterruptionType = "vsc" | "sc" | "red-flag";

export interface InterruptionSpec {
  type: InterruptionType;
  startLap: number;
  endLap: number;
}

/** Lap-time multiplier under interruption (relative to dry racing pace). */
export function interruptionLapTimeFactor(type: InterruptionType): number {
  switch (type) {
    case "vsc": return 1.30;  // ~30% slower than racing pace
    case "sc":  return 1.40;  // ~40% slower (following safety car)
    case "red-flag": return Infinity; // Session stopped -- no laps completed
  }
}

/** Pit-loss discount under interruption conditions. */
export function pitLossDiscountFactor(type: InterruptionType): number {
  switch (type) {
    case "vsc": return 0.65;  // ~35% reduction in pit loss
    case "sc":  return 0.40;  // ~60% reduction (field bunched, lower relative cost)
    case "red-flag": return 0.0; // Free tire change during red flag
  }
}
```

## Open Questions

### Resolved

1. **What is the right granularity for race timeline artifacts?**
   Use discriminated-union events (stint-start, stint-end, pit-event, interruption-start, interruption-end) with per-stint summary metrics (stint time, final tire wear, final SoC, effective grip range). Per-lap detail remains in the per-stint artifacts (LapTrace arrays). This gives Phase 4 both the event-level structure for timeline rendering and the aggregated metrics for factor decomposition without requiring Phase 4 to re-process raw lap traces for every comparison.

2. **Should branching support mid-stint forks or only stint-boundary forks?**
   Start with stint-boundary branching only. Rationale: (a) `StintResult.finalState` is a complete, validated state snapshot at stint boundaries; (b) mid-stint branching requires `runStint()` to accept an `initialState` parameter and resume from an arbitrary lap, which is a nontrivial change to a well-tested function; (c) Phase 4's STRA-04 interventions (mode changes, pit timing responses) can be adequately modeled as "change strategy from the next stint boundary onward." Design the `branchPoint` schema with a `branchType` enum that starts with `"stint-boundary"` and can later include `"mid-stint"` -- this preserves extensibility without building the harder feature now.

3. **How should experiment grouping relate to run lineage?**
   Use a lightweight `experimentTag` string field on RunRecord. Rationale: (a) lineage (parent/child) is structural -- it records causal history; (b) experiment grouping is conceptual -- it clusters runs exploring the same question; (c) siblings in lineage are not always part of the same experiment, and experiment members are not always lineage-related; (d) a simple string tag is sufficient for Phase 4's comparison workflow ("show me all runs tagged 'monza-2stop-vs-3stop'"); (e) if Phase 4 needs richer experiment objects, they can be built as a view layer on top of tags without schema changes.

4. **What reduced-order pit-lane loss model is appropriate?**
   Use the standard formula: `L_pit = (t_entry + t_exit - t_bypass) + t_stop`. Parameters should be circuit-specific configuration (part of circuit metadata or a separate pit-lane config), not hardcoded constants. Typical green-flag pit deltas range from 18-25 seconds depending on circuit. Under VSC, multiply by ~0.65; under SC, multiply by ~0.40; under red flag, pit cost is zero (free tire change). Service time for a clean tire-only stop is 2-3 seconds. These are engineering-inference values with well-documented provenance.

5. **How should race interruptions affect lap times in a single-car model?**
   Model interruptions as lap-time multipliers and pit-cost discounts. VSC: lap times ~30% slower, pit cost ~35% cheaper. SC: lap times ~40% slower, pit cost ~60% cheaper. Red flag: session paused, free tire change, session-length adjustment. The single-car model cannot simulate field bunching, so the "strategic advantage" of pitting under SC is captured purely through the pit-cost discount factor. This is an honest simplification -- the model explicitly labels the single-car limitation in its assumptions. Additional effects: tire cooling during slow laps (lower tire temperature toward ambient), reduced electrical harvesting opportunity, fuel saving.

6. **What tire-set allocation rules should the inventory model encode?**
   Use a configurable allocation table stored in the regulation preset's `values` field. Standard 2024-2025 allocation: 2 hard, 3 medium, 8 soft (13 total for standard weekends, 12 for Sprint). 2026 reduces to 5 dry compounds (C1-C5) but specific allocation numbers are not yet published; the model should accept configurable allocations rather than hardcoding any era's rules. Session return requirements (2 sets returned after each FP session) can be modeled as a simple bookkeeping deduction. The mandatory "use at least two different compounds in a dry race" rule should be validated pre-execution.

### Genuine Gaps

| Question | Criticality | Recommendation |
|----------|-------------|----------------|
