# 04 Decision Anchor

## Ontology 2: Regulation identity / version / capability model

O2 closes as a provisional recommendation on a family-primary hybrid ontology. Regulation family identity is the primary semantic handle for provenance, runtime discrimination, and historical continuity, but it is not sufficient by itself: capability modules must be explicit, document `schemaVersion` must remain independent from semantic identity, and cross-era comparison must use visible relation classes rather than assume family labels imply comparability. The minimum D4 constraint is therefore structural, not cosmetic: roadmap synthesis should split regulation work into distinct tracks for family cataloging, migration/canonicalization, execution compilation, and comparability/applicability registry work instead of hiding all of that under "type the presets."

## D5.A: Primary organizing axis and canonical runtime shape

D5.A closes as a recommendation. The primary axis is regulation family identity inside a hybrid ontology, not pure era labels, not pure capability bags, and not schema version. The canonical runtime shape should carry stable `familyId`, optional `familyVariantId`, raw source identity and hash, explicit capability-module presence or `kind`, stable semantic identifiers for comparison-relevant concepts, and override lineage. The most important Phase 4 planning constraint is that canonicalization must produce this semantic form before D1 projects to `ExecutionRegulationSnapshot`; Phase 4 should not keep inferring semantics from loose raw preset maps. The main unresolved question is where the first family boundaries should be drawn beyond the immediate 2026 baseline.

## D5.B: Schema versioning and migration posture

D5.B closes as a recommendation. `schemaVersion` is a storage-evolution axis and must not be collapsed into family identity. Both raw documents and canonicalized forms matter: raw authored presets remain the editable and auditable assets, while canonicalized semantics are the compiler target and the honest input to downstream comparison and lesson behavior. Old preset files and historical run snapshots do not need the same compatibility promise; preset files need forward migration within a supported window, while run snapshots need durable readability and reproducibility through stored raw-plus-compiled lineage rather than silent re-authoring into the newest preset form. The main unresolved question is whether the canonical semantic form eventually needs its own separately persisted public version once it becomes durable outside the compiler.

## D5.C: Comparability, applicability, and non-comparability semantics

D5.C closes provisionally. The load-bearing output is a small explicit relation vocabulary: `direct`, `derived`, `family-specific`, and `non-comparable`, with applicability treated as a precondition layer and fidelity / validation kept orthogonal. This is the main adjacent implication for D2 and D3: comparison surfaces, legend states, anchor fallback behavior, and lesson bindings should all be able to surface those relation classes honestly without treating every cross-era pairing as an overlay-worthy equivalence. A mild downstream caution follows from this: D2's accepted `semanticApplicability` surface slot is useful, but Phase 4 should avoid letting that single label become the entire internal ontology for cross-era relation states. The main unresolved question is the first metric and derivation registry the project should commit to for strategy and subsystem views.

## D5.D: Override model, semantic identifiers, and compile-to-execution handshake

D5.D closes provisionally. Regulation variants should use field-aware, family-aware typed patches anchored to a declared baseline family or family variant; shallow merge is too weak and unconstrained deep merge is too unsafe. Stable semantic identifiers are required beyond raw property names at least for families, capabilities, and comparison-relevant metric or concept IDs. The most important constraint D5 imposes on D1 and Phase 4 planning is that compilation must preserve semantic identity through the handshake: source preset identity and hash, family identity, variant or override lineage, a canonical semantic reference, and the explicit execution-relevant capability states used at runtime must survive into or alongside `ExecutionRegulationSnapshot`. The main unresolved question is the exact authoring and validation UX for those typed variant patches.
