# 01 Decision Anchor

## Contract 1: Compute execution boundary

C1 is closed as a recommendation: the durable boundary is a two-stage shape, `request compilation -> backend execution`, not a raw scenario-to-backend call. The stable contract belongs in `packages/domain`, with `apps/local-api` compiling scenario and preset references into a `CompiledSimulationRequest`, and a transport-neutral `SimulationBackend` owning submit/get/cancel/subscribe/listArtifacts/fetchArtifact. The first implementation should be a long-lived local TypeScript worker process around current `sim-core`, which preserves the 1-year Phase 4 path while keeping 3-year and 5-year Python/Rust/C++ sidecars or remote services viable. The main constraint this imposes downstream is simple: D2 and D3 must assume compute outputs arrive through jobs and artifacts rather than synchronous route returns, and D5 must assume regulation semantics are compiled before backend execution. The main open question is batch shape: one parent job, child jobs, or both.

## Contract 2: Job/event protocol

C2 is closed semantically and provisionally bound at the edge: use REST for submit/get/cancel/fetch and SSE for per-job event streaming, with the option to revisit the edge transport later without changing the event union. The event model is typed, sequence-numbered, and state-machine-based, with explicit `queued -> dispatching -> running -> cancelling -> cancelled/completed/failed` semantics, `artifact-ready` events for partial or final artifacts, and short-window replay rather than infinite event history. This constrains D2 to design around honest checkpoint-driven updates instead of monolithic full-run refreshes, constrains D3 to expect durable artifact fetch after reconnect rather than permanent event logs, and constrains D5 only indirectly by reserving comparability-aware provenance on events and artifacts. The main open question is when, if ever, richer full-duplex control makes WebSocket worth the extra complexity.

## Contract 3: Artifact / provenance contract

C3 is closed as the strongest recommendation in the deliberation. Every durable output should use a typed `ArtifactEnvelope` with separate `artifactId` and `artifactKey`, explicit lineage (`runId`, `runFamilyId`, parent references, checkpoint, revision), and provenance that includes harness/model/backend, fidelity and validation state, scenario snapshot hash, regulation source and execution snapshot references, and an input digest. D2 must consume `artifactKey`, `runFamilyId`, `anchorNamespace`, and partial/final status as its stable visualization substrate; D3 must build lesson bindings and view recipes on the same artifact-key and anchor-namespace model; D5 must populate the reserved cross-era applicability slot rather than invent parallel artifact identity rules. The main open question is how much addressability should live in an explicit `anchorSchema` manifest versus payload-local stable entity IDs.

## Contract 4: Regulation execution-flow slice

C4 is closed as a recommendation: canonicalize regulation documents before execution, send only a typed `ExecutionRegulationSnapshot` across the backend boundary, and store both the raw regulation document snapshot and the compiled execution snapshot for reproducibility. This snapshot should carry source preset identity and hash, family identity, and execution-relevant capability modules such as aero, electrical, and refueling. It requires removing the current 2026 electrical constants and no-refueling assumptions from sim-core and moving active-aero defaults out of `runService.ts` casts into the compiler. The main constraint on D5 is hard: whatever semantic model it chooses must still compile to this execution-facing snapshot cleanly; the main constraints on D2 and D3 are provenance-related, because artifacts and lessons need honest regulation family and applicability references. The main open question is the exact semantic axes D5 will choose for family identity, capability modeling, and cross-era comparability.
