# 03 Decision Anchor

## Ontology 1: Lesson concept graph and artifact-binding model

O1 closes as a recommendation on a stable lesson graph rather than a syntax choice. The primary educational identity is `conceptId` plus explicit role, difficulty, depth, scenario, and regulation-applicability axes, while `lessonId` names the concrete teachable unit that binds those axes to ordered steps and artifact references. `LessonUnit` should carry prerequisite and recommended-next edges, thin `LearningPath` curation for EDU-03, artifact bindings keyed to D1 `artifactKey` and D2 `recipeId`/`slotId`, and a body reference that points through a swappable adapter boundary rather than making Markdown, MDX, notebooks, or TypeScript modules the ontology. Assessment hooks remain adjacent and optional, not part of the minimum identity model. The most important adjacent constraint on D5 is hard: shared concepts across regulation families are related, not automatically comparable, and lessons must be able to mark bindings as `direct`, `derived`, `family-specific`, or `non-comparable` without D5 forcing false equivalence. The main open question O1 leaves is only the first implementation syntax and authoring ergonomics, not the graph shape.

## Contract 6: Annotation-anchor / view-recipe contract, content side

Content-side C6 closes only provisionally: lesson content must consume D2's accepted substrate rather than inventing its own. Lessons bind through `recipeId`, `slotId`, `ArtifactAnchorRef`, and D2's typed `AnchorResolutionStatus`, and guided steps may change recipe, focus, cursor, brush, selected branch, selected strategies, and pinned anchor only through D2's C5 action substrate. Fallback behavior is closed semantically: `artifact-missing` and `anchor-missing` degrade to panel-level explanatory callouts with visible reason codes; `filtered-out` first tries local reveal through D2 actions; `not-applicable` surfaces honest cross-era or cross-context inapplicability rather than pretending equivalence; `renderer-unavailable` preserves lesson traversal through accessible text and slot-level fallbacks. D3 does not request any reopening of D2 anchor identity or view-recipe slot semantics, and additive pedagogical metadata should remain lesson-owned and keyed to existing `recipeId`/`slotId` values. The one open issue is interface completeness: D2 names an `AnchorRegistry` but does not define its minimal `register` / `update` / `remove` / `resolve` / `subscribe` semantics, so D3 imposes a narrow Phase 4 planning constraint and identifies that interface as the only legitimate possible Wave 2B-iii input if earlier formalization is desired.

## D3.A: Body format and adapter boundary

D3.A closes on the adapter boundary and deliberately leaves the initial body syntax provisional. The stable unit is a normalized lesson body keyed by `stepId`, preserving accessible text and media metadata regardless of whether the source is Markdown, MDX, TypeScript modules, or notebook-like cells. Because the first realistic authoring mode is developer- or domain-author-authored content in-repo, likely with AI-assisted drafts and human technical review, D4 should plan for a file-based first implementation and not assume a rich notebook runtime or a separate CMS. The unresolved question is which concrete syntax gives the best preview and review loop once Phase 4 scopes tooling.

## D3.B: Lesson graph and progression semantics

D3.B closes as a recommendation. `roleTags` remain useful but are not enough to define learning flow; EDU-03 needs a thin curated `LearningPath` overlay so role-specific onboarding does not collapse into simple filtering. Difficulty and depth are explicit axes but not a global total order across all concepts and roles, and shared `conceptId` does not imply interchangeability across regulation contexts or lesson variants. D4 should treat this as a planning input for the first content schema, validation rules, and lesson-path fixtures. The main unresolved question is how much path-level metadata Phase 4 needs beyond entry lessons and milestone concepts.

## D3.C: Artifact binding, guided state, and fallback behavior

D3.C is provisional because the semantics close but the registry surface is still additive work. D3's main constraint on optional D2 revision is narrow: if the initiative wants a formal 2B-iii pass, it should only codify the minimal `AnchorRegistry` API D3 assumes, not reopen anchor identity, failure modes, or shared interaction semantics. D4 should otherwise make registry completion a hard pre-implementation task in Phase 4 planning. The open question is whether that completion belongs in a formal D2 addendum or in the Phase 4 plan itself.

## D3.D: Authoring, validation, preview, accessibility, and thin-client workflow

D3.D closes at the architectural commitment level: lesson authoring, preview, validation, accessibility, and apollo-thin-client viability are part of the educational architecture, not operational garnish. Lessons need in-app preview against canonical artifacts and view recipes; validation must cover schema, prerequisite integrity, recipe and anchor resolution, fidelity and validation mismatches, regulation applicability, accessible text, keyboard-only traversal, and caption/transcript presence; runtime lesson surfaces must visibly carry fidelity, validation, and non-comparability markers. The strongest D4 implication is planning scope: educational architecture now includes schema work, preview fixtures, validation tooling, and shell consumption of recipe variants before substantial lesson growth. The main unresolved question is how far the first wave should go on richer media and dense spatial narration beyond text-first guided steps.
