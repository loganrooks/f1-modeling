# 02 Decision Anchor

## Contract 4: Renderer-agnostic visualization surface

C4 is closed only as a provisional recommendation: the stable decision is a three-layer visualization surface, `ArtifactEnvelope<TPayload> -> ViewAdapter<TPayload, TViewModel> -> RenderSurfaceProps<TViewModel>`, with renderer choice handled by a per-`ViewFamily` registry rather than by ad hoc chart selection. The first renderer family should be semantic SVG/DOM because it best matches the current repo's migration seams, accessibility obligations, and annotation-heavy early product surface, while dense traces must retain a `dense-canvas` promotion path and future dense spatial/event panels may later add a `gpu-layer` family. D3's main constraint is that lesson content must target recipe ids, panel slots, and renderer-neutral anchors instead of raw DOM nodes or package-specific chart APIs. D5's adjacent constraint is that comparison artifacts must populate `semanticApplicability`, fidelity, and validation provenance because the renderer contract assumes those states are visible in every comparison surface. The main unresolved question is package binding inside the semantic SVG family: stable low-level visx remains React 18-peered as of 2026-04-11, so a visx-first implementation is only provisionally viable via the alpha line and cannot be treated as a settled architectural decision.

## Contract 5: Shared interaction state contract

C5 is closed as a recommendation. The shared state shape should remain small and semantic: active recipe id, focused panel id, shared cursor, committed brush window, selected strategies, selected branch, pinned anchor, and focused lesson step. Propagation should be client-local and selector-driven, with panels publishing data-domain coordinates rather than pixels and subscribing only to the slices they actually consume; context-wide fan-out is not the intended contract. D3's main constraint is that lesson stepping, guided focus, and pinned annotations must flow through the same action API as ordinary chart interaction rather than inventing a parallel lesson-only state model. D5's adjacent constraint is indirect but important: cross-era comparison states need to fit into the same shared cursor/selection substrate without assuming every compared value is directly comparable. The main unresolved question is whether the eventual implementation should be a small internal `useSyncExternalStore`-style store or a library-backed equivalent; the contract closes the semantics and subscription model, not the package name.

## Contract 6: Annotation-anchor / view-recipe contract

C6 is closed as a provisional recommendation. Anchor identity should be logical-first and artifact-relative: `runFamilyId + artifactKey + anchorNamespace + anchorPath`, with optional `artifactId` or `revision` only when an exact historical instance must be pinned. Resolution should always yield a typed outcome, including explicit failure modes such as `artifact-missing`, `anchor-missing`, `filtered-out`, `not-applicable`, or `renderer-unavailable`, because D3 must be able to react without guessing why a lesson target failed to bind. View recipes should name canonical panel-slot arrangements, preferred renderer families, artifact bindings, interaction domains, and responsive collapse order; D3 consumes recipe ids and slot semantics, but should not redefine them. D5's adjacent constraint is that cross-era non-comparability must surface all the way through anchor fallback behavior rather than only in background metadata. The main unresolved question is how much additive metadata D3 will need around recipes for pedagogical sequencing; that should be additive, not a reopening of anchor identity or resolution semantics.

## D2.A: Workspace shell implications

D2.A is scoped out with a concrete handoff. The current three-zone shell in `App.tsx` and `WorkbenchShell` is not sufficient for the envelope D2 inherits, so a follow-on foundation plan needs to implement a shell that consumes `ViewRecipe` and named panel slots rather than a hardcoded tuple. The important closure here is location, not full design: shell implementation is adjacent to D2 and must land before substantial new D2-era view growth, but it is not the same thing as the renderer contract itself.

## D2.B: Design system foundation

D2.B is closed with a limited scope. New D2-era panels must consume a shared visualization token layer for typography, spacing, panel chrome, axes, overlays, branch colors, fidelity states, and comparability states. A full design system is explicitly deferred; the near-term contract is "shared tokens now, broader design-system maturation later." This means legacy panels can remain frozen until migrated, but no new substrate-native panel should introduce private styling constants that recreate the current duplication problem.

## D2.C: Accessibility constraints

D2.C is closed as a hard commitment to WCAG AA minimum. Semantic SVG/DOM is preferred for annotation-heavy panels because it preserves focus management and accessible semantics most directly, while Canvas or future GPU panels are valid only if they ship with accessible proxy targets and non-visual summaries. Keyboard interaction is non-optional for cursor, brush, selection, and anchor pinning, and every annotation anchor must carry accessible text that screen readers can announce. The main open question is not whether to do accessibility, but how far the first wave should go in narrating dense spatial relationships beyond summary text and anchored callouts.

## D2.D: Cross-device / thin-client rendering

D2.D is closed at the architectural commitment level and left open only on empirical verification. Apollo-over-Tailscale is the reference client path, so interaction responsiveness must remain local to already-fetched artifacts and shared client-side state; no hover, scrub, or brush flow may depend on a network round-trip to dionysus. Responsive variants belong in view recipes, focus mode is part of the degradation ladder rather than an afterthought, and touch is not a v1 requirement but the input model must remain pointer-agnostic so touch can be added later. The main open question is the measured SVG-to-Canvas crossover on real Apollo hardware once the benchmark harness from R1.5 exists.
